# Розділ «Замовлення» — повний опис

> Як влаштовані й працюють Замовлення в AiM Skill: що є, як пов'язано, що можна внести і куди ця інформація потрапляє.
> Джерела: `src/pages/Orders.jsx`, `src/pages/OrderCard.jsx`, `src/lib/orders.js`, `src/components/Kanban.jsx`.
> Останнє оновлення: 2026-08-18.

---

## 1. Що це таке і три напрямки

Замовлення (`orders`) — це **заявка/угода з клієнтом** від першого контакту до закриття. Є **три типи** (`trade` — синій, `service` — фіолетовий, `agent` — бірюзовий), які відрізняються лише кольором/змістом; **статуси спільні для всіх** (`src/lib/orders.js`):

| # | Ключ | Статус |
|---|---|---|
| 1 | `new` | Новий |
| 2 | `processing` | В опрацюванні |
| 3 | `ordering_supplier` | Замовлення у дистрибютора |
| 4 | `shipped` | Відвантажено |
| 5 | `paid` | Оплачено |
| 6 | `closed` | Закрито |

Статус рухається **вручну** менеджером — випадайка «Статус» у вкладці «Деталі» (можна поставити будь-який). Статус — **єдиний контрол стану заявки** (концепцію «Наступна дія» прибрано 2026-08-18; набір статусів спрощено з 12 до 6 того ж дня). Старі статуси переназначені міграцією 032, а код показує їх через легасі-мапу.

**Головний принцип:** замовлення **не має фінансового впливу** саме по собі. Борги, P&L, ПДВ, склад рахуються лише коли з'являється **реальний документ** (накладна/акт) або **банківська транзакція**. Замовлення — це «воронка» й підготовка угоди.

## 2. Реєстр замовлень (`Orders.jsx`)

**Що видно:** KPI зверху (Активних · Прострочено · Сума в роботі) + список.

**Два вигляди** (перемикач справа):
- **Таблиця** — № · Клієнт · Тип · Статус · Сума (сортовані кліком по заголовку). Прострочені підсвічені червоним.
- **Канбан** (`Kanban.jsx`) — колонки = статуси. Фільтр за типом показує повний pipeline цього типу; змішаний режим — лише наявні статуси в канонічному порядку.

**Фільтри:** Всі · Прострочено · Торгівля · Послуги · Агент · Архів.
У фільтрі «Архів» показується підсумок **Виграно / Програно + суми + win-rate**.

**Що можна внести тут:** кнопка «Нове замовлення» → модалка (напрямок, клієнт\*, сума-план, опис). При збереженні:
- генерується унікальний `order_number` через `nextOrderNumber()` (атомний механізм — послідовність у БД, стійка до гонок і видалень),
- створюється рядок у `orders` зі статусом `new`.

**«Прострочено»** рахується автоматично: КП надіслано >48 год без відповіді (`proposalOverdue`) **або** сплив `payment_due_date` субзамовлення (`paymentOverdue`).

## 3. Картка замовлення (`OrderCard.jsx`) — шапка

У шапці — **степер статусів** (6 етапів): клік по етапу миттєво переводить замовлення в цей статус (єдиний контрол стану). Пройдені етапи — зелені з галочкою, поточний — синій. Перехід у «Закрито» проставляє `closed_at`, вихід із «Закрито» — скидає.

Дії в шапці:
- **Копіювати** — дублює замовлення разом з усіма товарами (`order_items`), новий №, статус `new`.
- **Архівувати** — з вибором результату **Виграно / Програно / Без результату** (`orders.archived_at` + `orders.outcome`). Архівні приховані з реєстру й не рахуються в KPI. Відновлення — «Відновити». Результат можна змінити прямо в банері архіву.
- **Видалити** — двокрокове підтвердження; **блокується**, якщо до замовлення прив'язані документи (пропонує архів). Без документів — БД каскадом прибирає КП/субзамовлення, а документи/рухи/листи відв'язуються (`SET NULL`).

Далі — **5 вкладок**: Деталі · Товари · КП · Документи · Субзамовлення.

## 4. Вкладки — що вносиш і куди воно йде

### 📋 Деталі (`DetailsTab`)
**Вносиш:**
- **Клієнт** (ContractorSelect — вибрати наявного або створити нового);
- **Тип закупівлі** (**Пряма / Тендер**); при виборі «Тендер» з'являється поле **«Ідентифікатор закупівлі»** (`orders.procurement_id`, напр. номер Prozorro);
- **Дата закриття заявки** (`closed_at`, редагована);
- **Опис**.

**Тільки перегляд:** **Дата створення** (`created_at`).
**Куди йде:** таблиця `orders`.
**Що прибрано з вкладки (2026-08-18):** «Сума» (є в шапці й у «Товарах») і «Статус» (тепер степер у шапці). Тип закупівлі впливає на PDF «Замовлення постачальнику» та «Розрахунок для інвестора».

### 📦 Товари (`ItemsTab`) — серце замовлення
Позиції зберігаються в `order_items`. Кожна: назва + `product_id` (прив'язка до довідника `products`), код (`sku`), к-сть, од., **закупівля** (`cost_price`), **націнка %**, **ціна продажу** (`unit_price`), **ПДВ %**, **тип ціни** (ціни з ПДВ / без ПДВ).

**4 способи внести позиції:**
1. **Вручну** — кнопка «Позиція».
2. **З прайсу** — `PricePickerModal`, пошук по всіх прайсах постачальників (`supplier_prices`); закупівля = ціна прайсу, продаж = роздріб, запам'ятовує постачальника (`supplier_id`), ціни трактуються як з ПДВ.
3. **Специфікація (AI)** — завантажуєш договір/специфікацію (.docx / PDF / фото) → Claude витягує товарні позиції з цінами.
4. **Собівартість (AI)** — завантажуєш рахунок постачальника → AI зіставляє його рядки з наявними позиціями (за кодом, тоді за назвою — токенна схожість ≥0.4) і проставляє лише `cost_price`. **Нових позицій не додає** (рахунок може покривати кілька замовлень); собівартість зводиться до бази ПДВ рядка, щоб маржа лишалась net-to-net.

**Розрахунки на льоту:** маржа (net-to-net), націнка (двобічна — задав закупівлю → рахує продаж, і навпаки), масова націнка на всі позиції, підсумки Без ПДВ / ПДВ / Всього з ПДВ.

**Куди йде при «Зберегти»:**
- повністю **переписує** `order_items` замовлення;
- для вільних назв створює/знаходить товар у довіднику `products` через `resolveProduct` (позиції стають переюзними);
- **синхронізує `orders.total`** = сума цін продажу з ПДВ;
- кнопка **«Розрахунок для інвестора»** генерує PDF (рентабельність, капітал, ROI) — не зберігається.

### 📄 КП (`ProposalsTab`)
Версії комерційних пропозицій у `commercial_proposals` (jsonb-позиції, версія, статус, сума).
**Вносиш:** «Нова версія» (префілиться товарами замовлення) → редагуєш позиції (назва, к-сть, од., ціна, ПДВ, тип ціни) → «Зберегти чернетку».
**Дії:** Переглянути (PDF у новій вкладці, маркетинговий дизайн, опційно з печаткою) · Надіслати (статус `sent` + `sent_at`; для trade зі статусу `new` рухає замовлення на `proposal_sent`) · Прийнято / Відхилено · Видалити.
**Важливо:** КП **не зберігається в Документи** і **не впливає на борги/P&L** — живе лише всередині заявки, переглянути можна будь-коли повторним кліком.

### 🗂 Документи (`DocumentsTab`)
Дві секції:
- **ЗГЕНЕРОВАНІ** — кнопки **«Рахунок» / «Видаткова»** відкривають `DocGenModal` з префілом товарів замовлення. Збереження пише в `generated_docs` + **дзеркало в `documents`** (`source='generated'`, `order_id`) → документ **з'являється в розділі «Документи», картці контрагента і ВПЛИВАЄ на борги/P&L** (видаткова = дебіторка; рахунок — NON_DEBT). Видаткова також може списати склад (FIFO через чекбокс у майстрі). Дії на рядку: Переглянути / Завантажити / Редагувати / Видалити.
- **ПРИВ'ЯЗАНІ** — реальні скани. Кнопка **«Прив'язати»** (`AttachDocsModal`, за замовч. показує документи клієнта) виставляє `documents.order_id`; «Відв'язати» повертає в `null`. Клік по рядку відкриває `DocModal` (перегляд/розпізнавання/перевірка).

Саме **тут замовлення отримує фінансову вагу** — через реальні або згенеровані документи.

### 🚚 Субзамовлення (`SuppliersTab`)
Замовлення дистрибюторам у `supplier_orders` + `supplier_order_items`.
**Вносиш:**
- **«Сформувати з товарів»** — групує `order_items` за постачальником (`supplier_id`) і створює по одному субзамовленню на постачальника (`source='auto'`); позиції без постачальника → група «Без постачальника». Повторне формування заміщує лише `auto`, ручні (`source='manual'`) лишаються.
- **«Вручну»** — постачальник, сума, відстрочка (дн) → рахує `payment_due_date`.

**Дії:** зміна постачальника / статусу (Новий · Замовлено · В дорозі · Отримано · Оплачено), помітка **«замовлено»** на кожній позиції (+ «виділити всі» → статус `ordered`, замовлені закреслені, лічильник «N з M»), PDF **«Замовлення постачальнику»** (без цін/сум — лише перелік з кодом + реквізити клієнта + тип закупівлі).
**Куди впливає:** `payment_due_date` формує ознаку «прострочено» в реєстрі.

## 5. Як усе пов'язано (модель даних)

```
orders (client_id → contractors)
  ├── order_items ──────→ products (product_id), supplier_prices (з прайсу), contractors (supplier_id)
  ├── commercial_proposals   (КП, лише всередині заявки)
  ├── supplier_orders ──→ supplier_order_items   (субзамовлення)
  ├── generated_docs ───→ documents (дзеркало, source='generated')  → БОРГИ / P&L / ПДВ
  ├── documents (order_id)  ← прив'язані реальні скани              → БОРГИ / P&L / ПДВ
  │        └── transaction_documents → bank_transactions            → ОПЛАТИ
  └── stock_movements (order_id)                                    → СКЛАД (FIFO)
```

**Куди «просочується» внесена в замовлення інформація:**
- **Товари** → довідник `products` (переюз), сума замовлення, маржа, інвестор-розрахунок.
- **Згенеровані / прив'язані документи** → розділ «Документи», картка контрагента, **дебіторка/кредиторка** (авто = документи − транзакції), **P&L** (Аналітика), **звіт ПДВ**, звіт **«Рентабельність»**.
- **Видаткові** → **складські рухи** (списання FIFO).
- **Субзамовлення** → PDF постачальнику, контроль оплат/прострочень.
- **КП** → нікуди поза заявкою (тільки PDF на вимогу).

**Джерела створення замовлень** (усі дають той самий `orders`): веб-форма, копіювання, Telegram-бот (`api/telegram.js`), API-бот (`api/bot.js`), заявка з листа (`api/order-from-email.js`). Номер скрізь генерується атомно через `next_order_number()` / фолбек `max+1`.

## 6. Нюанси й технічні знахідки

- **Сума замовлення** автоматична, коли є товари; ручна — лише для послуг/агента без позицій.
- **Маржа скрізь net-to-net** (без ПДВ); «тип ціни» лише задає, як введені числа (з ПДВ чи без).
- **Номери замовлень унікальні** — гарантовано послідовністю `orders_number_seq` + унікальним індексом `orders_order_number_uniq` (міграція 031). Ні видалення, ні одночасне створення з різних джерел більше не задвоюють номер.
- **7 вкладок.** Окрім п'яти основних, є ще `Транзакції` (прив'язані банк-транзакції) і `Склад` (складські рухи замовлення) — обидві read-only, часто порожні на ранніх статусах. Кандидати на злиття/скорочення (їхній сенс можна винести в шапку/Документи).

## 7. Таблиці БД, задіяні в розділі

| Таблиця | Роль |
|---|---|
| `orders` | Заголовок замовлення (тип, статус, клієнт, сума, архів, результат, тип закупівлі) |
| `order_items` | Позиції товарів (закупівля, продаж, ПДВ, постачальник, прив'язка до `products`) |
| `commercial_proposals` | Версії КП (jsonb-позиції, статус, `sent_at`) |
| `supplier_orders` / `supplier_order_items` | Субзамовлення дистрибюторам + їхні позиції (помітка «замовлено») |
| `generated_docs` | Згенеровані рахунки/видаткові (дані для регенерації PDF) |
| `documents` | Прив'язані скани + дзеркала згенерованих (`order_id`, `source='generated'`) |
| `stock_movements` | Складські рухи замовлення (`order_id`) |
| `transaction_documents` → `bank_transactions` | Оплати через прив'язані документи |
| `contractors` | Клієнт (`client_id`) і постачальники (`supplier_id` у позиціях/субзамовленнях) |
| `products` / `supplier_prices` | Довідник товарів і прайси постачальників |
